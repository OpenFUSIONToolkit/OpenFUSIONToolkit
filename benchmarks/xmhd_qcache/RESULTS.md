# xMHD quadrature-point cache: design, validation and results

This is the summary of the work that moved the 3D xMHD (MUG) nonlinear residual and Jacobian onto a
precomputed quadrature-point cache. The code is in `src/fem/fem_quad_cache.F90` and `src/physics/xmhd.F90`.
The harness used for all timings is described in `README.md`.

The detailed reports and raw results (JSON/CSV per run, perf reports, equivalence logs, valgrind output) are
kept on the development branches of the fork and are not part of this tree:

| branch | content |
|---|---|
| `claude/xmhd-qcache-phase0` | harness, baseline profile of `main` (`phase0_baseline.md`, `results/baseline.*`, `results/perf_*`) |
| `claude/xmhd-qcache-phase1` | conditional `log2phys`, partition-aware lock-free scatter (`phase1_results.md`) |
| `claude/xmhd-qcache-phase2` | `fem_quad_cache` module, kernel benchmark (`phase2_results.md`, `results/phase2_kernels_*`) |
| `claude/xmhd-qcache-phase3` | NL residual on the cache (`phase3_results.md`, `results/p3ab_*`, `results/phase3_qcheck.log`) |
| `claude/xmhd-qcache-phase4` | Jacobian on the cache, CSR position map (`phase4_results.md`, `results/p4ab_*`, `results/phase4_*`) |

Those reports use the option values of the development branches. In this document all values are the final
ones: `xmhd_qcache=0` is direct basis evaluation and `xmhd_qcache=1` is the cache (`xmhd_qcache=2` on the
Phase 3/4 branches). The development branches also had a "FULL" cache mode (physical basis stored per cell and
quadrature point, `xmhd_qcache=1` there). It was never used for the Jacobian, was at best 1.0-1.2x faster than
direct evaluation on tets for the residual at up to 1.7 GB of extra memory, and has been removed.

## Options

| `xmhd_options` entry | default | meaning |
|---|---|---|
| `xmhd_qcache` | 1 | 0 = evaluate basis functions directly at every quadrature point (reference implementation), 1 = quadrature-point cache for the NL residual and for the Jacobian of every level on the finest mesh |
| `xmhd_jac_posmap` | 1 | precomputed CSR positions of the local Jacobian entries (native matrices); 0 = search the column lists |
| `xmhd_jac_posmap_maxmb` | -1 | skip the position map of a level that needs more memory per rank [MB] (negative: no limit) |
| `xmhd_coarse_quad` | F | **experimental**: integrate the Jacobian of coarse polynomial MG levels with their own (lower) quadrature order |

**BLAS threading.** The Jacobian calls `dgemm` from inside OpenMP parallel regions. The BLAS must run
single-threaded there: OFT's `build_libs.py` OpenBLAS (single-threaded `USE_THREAD=0` by default,
`USE_OPENMP=1` with `--oblas_threads`), Ubuntu's `libopenblas0-openmp` and MKL do this; with a pthreads
OpenBLAS (Ubuntu's default `libopenblas0-pthread`) set `OPENBLAS_NUM_THREADS=1`. With the pthreads build the Jacobian build stopped scaling: tet p4 took 2.33 s at 1
OpenMP thread and 2.21 s at 4 (hex p3: 3.06 s and 2.10 s); with `OPENBLAS_NUM_THREADS=1` it took 0.71 s at 4
threads (hex p3: 0.94 s).

## Design

**Cache (`fem_quad_cache`).**
- `oft_qcache_geom` stores, per mesh and quadrature rule, the three independent logical gradient vectors (`gop`),
  their cross products (`cgop`) and the Jacobian determinant: once per cell for straight tets and affine hexes,
  once per (cell, qp) otherwise. It also stores the orientation state of every edge and face of each cell, and
  optionally the physical quadrature points (only when shaping functions are set) and thread-partition boundary
  flags.
- `oft_fem_qcache` stores, per FE space (Lagrange, H^1, H(Curl)), cell-independent reference tables of the
  logical components of every basis function: one block of rows per (entity, orientation state), generated by
  calling the standard evaluators on an internal template mesh that enumerates all states. Physical values,
  gradients and curls are rebuilt with the per-cell geometry.
- Orientation transforms are fitted at setup. Hexes: all states are signed permutations of state 1. Tets:
  Lagrange, edges and H^1 faces of order <= 3 are signed permutations, H^1 faces of order >= 4 are dense
  combinations of the face's, its edges'/vertices' and the interior functions, and H(Curl) faces (p >= 2) are
  not in the span of the cell's H(Curl) functions at all (they differ by gradients, which OFT keeps in the
  separate Grad(H^1) space); those use their own dense per-orientation table blocks.
- Cell-batched kernels (`fem_qcache_interp_cell`, `fem_qcache_accum_cell`) map a cell's coefficients to the
  canonical frame once, contract them with the canonical table for all quadrature points at once (a
  `nce x (3 nqp)` by `nce x nfld` product, unit stride), add the per-orientation blocks, and apply the per-qp
  geometry. `fem_qcache_eval_cell` builds the physical basis of a cell at all qp exactly from gathered rows.

**NL residual.** The pointwise physics is one routine, `xmhd_resid_qp`, shared by the direct and the cache
paths. It maps the unpacked fields at a quadrature point to test-function fluxes (with `det*w`). The cache path
(`xmhd_resid_qcache`) gathers each cell's coefficients, reconstructs all fields at all qp, packs and unpacks
them exactly as `xmhd_interp_apply` does (so all scale factors and the `dV(:,k)=grad(V_k)` convention are
shared), calls `xmhd_resid_qp`, contracts the fluxes, and scatters with atomics only for cells on thread-partition
boundaries.

**Jacobian.** The linearized physics is one routine, `xmhd_jac_qp`, which returns a per-qp coefficient tensor
`D` (at most 43 x 43) coupling the value/gradient (Lagrange), value/curl (H(Curl)) and gradient (Grad(H^1))
components of every test and trial field. Both paths form the local matrices of a cell with the same batched
contractions: `xmhd_jac_wform` contracts each used row of `D` with the trial functions, and `xmhd_jac_contract`
does two `dgemm` calls per row space (value and derivative components, `K = ncomp*nqp`). The paths differ only in
how basis functions and fields are evaluated. Coarse polynomial levels live on the finest mesh and use the
finest level's quadrature rule and geometry (shared), with their own basis tables. Scaling, boundary conditions,
revolved-periodic packing and assembly are one shared routine (`xmhd_jac_finish_cell`).

**CSR position map.** For every cell and (row space, column space) pair the map stores the position of each
local entry in the native matrix's value array (int32, row-major), so assembly needs no column search. It is
built on the first Jacobian build of a level and rebuilt if the matrix structure changes. Cells that share no
DOFs with another thread partition add without locks; other cells use per-field locks.

## Validation

All equivalence checks are in-process comparisons in `src/tests/physics/MUG/test_MUG_qcache.py` (driver
`xmhd_bench`, `mode='qcheck'`) and `src/tests/fem/test_fem_qcache.py`.

- **Basis cache** (`test_fem_qcache.py`, 20 tests): every (cell, qp) against the direct evaluators on
  straight, periodic and curved tets p=1-4, affine and curved hexes p=1-3, 2 MPI ranks, and the p-1 levels at
  the finest quadrature: values, gradients, curls, field reconstruction, accumulation, local matrices, per-qp and
  cell-batched kernels. Largest difference 3.4e-14 relative, ~1e-15 in most checks.
- **NL residual** (35 configurations: physics option sets incl. Hall, Braginskii, two temperatures,
  hyper-resistivity/diffusivity, all shaping functions, `eta_temp`/`res_profile`, floors and floor sources,
  gravity, solid cells, normal/tangential velocity BCs, revolved periodicity; tets p2-p4, curved tets, hexes
  p2/p3, p-MG, 2 MPI ranks), each with `dt>0`, `dt>0` with previous-step fields and the `dt<0` diagnostics:
  largest difference 2.9e-14 relative to the largest entry of the same equation; diagnostics agree to 1.4e-15,
  floor flags exactly.
- **Jacobian**: per level, cache + position map and direct + position map against direct + column search.
  Largest entrywise difference relative to the row maximum 6.5e-14, except curved cells (7e-13 at p=2,
  2.4e-12 at p=3, in the Te/H(Curl)-curl couplings, from a different summation order with cancellation); products
  with random vectors agree to 1.7e-15. The position map alone changes only the assembly order (5.5e-16).
  The batched-contraction Jacobian also agrees with the original per-qp implementation to 5.9e-15 (checked across
  builds on the Phase 4 branch).
- **Run mode**: linear and nonlinear iteration counts are identical at every time step for NK (tet p2, tet p3
  p-MG) and MFNK (tet p3 p-MG) between the original code, `xmhd_qcache=0` and `xmhd_qcache=1`. Final field norms
  differ by <= 1.1e-9, the same as repeated runs of one configuration at 4 threads (OpenMP reduction order).
- **MUG regression subset** with the defaults: alfven/sound p2 NL and linear (incl. 2-rank NK/MFNK), hex p2,
  sound p3 MG, `test_MUG_visc.py`, `test_MUG_gyro.py`, `test_MUG_hall.py` pass.
- Runtime checks (`-fcheck=all` debug build) and valgrind memcheck of cache-path runs report no errors.

### PETSc linear algebra backend

PETSc matrices keep the generic `fem_mat_add_local` assembly (with per-field locks; no position map), and the
residual is written through `get_local`/`restore_local` on PETSc vectors. Validated with PETSc 3.23.7 (the
`build_libs.py` default: `--build_petsc=1 --petsc_version=3.23 --petsc_openmp=1 --petsc_superlu=1`), MPICH
4.2.3, GCC 14, OpenMP, `--oft_use_lto=0`, Release; Ubuntu 24.04 cloud VM, 4 vCPUs. PETSc 3.23 is built on the
integer-handle `mpi` module, so OFT uses the header-based MPI interface.

- **Equivalence** (`test_MUG_qcache.py`, 13 `*_petsc` variants: two- and single-temperature, Hall, viscosity
  with `nu_par`/`nu_gyro`, floors/solid cells, hex p2, revolved periodic tet/hex, p-MG p3 and p4, 2 MPI ranks
  with and without p-MG). `xmhd_jac_check` compares the Jacobians of every level through products with three
  fixed random vectors (the CSR values of PETSc matrices are not accessible; native matrices are also compared
  entrywise). Residual blocks agree to 2.7e-14 relative to the largest entry of the same equation (1.6e-15
  relative to the whole residual), diagnostics to 5.7e-16; Jacobian products to 6.8e-16 on all 34 level
  comparisons. The 35 native variants are unchanged and pass in the same build.
- **MUG regression suite** (`src/tests/physics/MUG`, defaults incl. `xmhd_qcache=1`): all 141 PETSc variants
  run. Non-slow, native and PETSc variants together: 204 passed, 26 skipped (excluded combinations, eg.
  matrix-free with PETSc), 0 failed. Slow PETSc variants (alfven, sound and their Lagrange versions): 33 passed, 40 skipped (excluded combinations).
  `src/tests/fem`: 584 passed.
- **Native vs PETSc, run mode** (1 OpenMP thread, block-Jacobi + LU so that both backends factor with SuperLU):
  linear and nonlinear iteration counts are identical at every time step for tet p2 NK (`tet_p2_run`; linear
  8/4/25/29/33, nonlinear 5/4/3/3/3) and tet p3 p-MG NK (`tet_p3_mg_run --size 0.5`; linear 6/4/12/15/20,
  nonlinear 5/4/3/3/4), and with `xmhd_qcache=0` under PETSc (final norms equal to 1e-15). Final norms differ
  between the backends by 1e-11 (p2) to 3e-9 (p3 p-MG, B) relative. This comes from the initial condition:
  `xmhd_bench` projects it with CG to `atol=1e-10`, and the native and PETSc CG solutions differ at that level.
  With the projections converged to 1e-15 the NL residual and Jacobian matvec norms of the initial state agree
  between the backends to 6e-15 (profile mode, tet p2).
- **Not #457** (seen during this validation; fixed by separate upstream PRs, applied only locally):
  - Run-mode PETSc with an XML block-Jacobi preconditioner (`nlocal>0`) crashes in `PCSetUp_ASM`/`ISSort` with
    PETSc 3.23; fixed by #459. The PETSc runs above used #459 applied locally (native tet p2: this branch
    alone); the p3 p-MG comparison used #459 and #456 for both backends.
  - Native p-MG with an exact (SuperLU) LU smoother gives NaN from round-off in the native global reductions,
    with both implementations and with the position map off. This is also the cause of the native
    `test_alfven.py::test_nl_r1_p3`, `test_lin_r1_p3` and `test_lin_r1_p3_mpi[False]` failures in SuperLU
    builds (their PETSc variants pass). All three pass with #456 applied.
  - Intermittent `free()` segfaults right after setup with an XML MG preconditioner (8 of 8 runs in one
    environment, 0 of 8 with the fix): undefined pointer outputs of the XML extractors, fixed by #456.

## Performance

Reference machine: Intel Xeon (Cooper Lake) cloud VM, 4 vCPUs, 15 GB RAM, shared host (run-to-run noise
+-15-30%). Ubuntu 24.04 system libraries (`oft-build` skill, section 5): GCC 13 `-O2` + LTO, OpenMPI 4.1,
OpenBLAS 0.3.26 (OpenMP variant for the multi-threaded Jacobian runs), SuperLU, METIS. `run_bench.py` default
matrix with ILU block-Jacobi; configurations interleaved, 2 repetitions each, medians shown. Meshes and physics:
see `README.md`.

## Remaining hotspots and next steps

- Jacobian build (tet p3, 1 thread, `perf`): scatter with the position map 27% (memory bound), trial-function
  contraction (`xmhd_jac_wform`) 26%, `dgemm` 17%, `xmhd_jac_qp` 8%, BCs/scaling 6%, field reconstruction 6%,
  basis rebuild 5%. On hexes p3 `dgemm` is 57%.
- NL residual (tet p3, cache): ~75% of the time is the two small dense contractions per cell and quantity
  (reconstruction and accumulation), which run at ~2 GFLOP/s per core in the generic `-O2` (SSE2) build;
  `-march`-level vectorization or batching cells would help.
- Time stepping is now dominated by the linear solve and preconditioner: reuse of the symbolic ILU/LU
  factorization, retuned update frequencies (`xmhd_prefreq`, `nl_update`) and block CSR storage are the next
  candidates.
- GPU: the cell loops have the structure of batched kernels (indexed gathers, cell-independent tables that fit in
  shared memory up to p=3, a pointwise kernel without allocation or type-bound calls, batched GEMMs and a scatter
  with precomputed positions). `D` is sparse with a static pattern, and the module settings read by the pointwise
  kernels would need to be collected into one constant structure.
- `xmhd_massmatrix_apply` (linear runs) and PETSc matrices (no position map) still use the direct evaluation and
  `mat_add_local`.
